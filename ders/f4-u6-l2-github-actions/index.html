Anlatım01 / 12

CI/CD: "benim makinemde çalışıyordu"nun sonu

CI/CD iki fikirdir:

  • CI (sürekli entegrasyon): her küçük değişiklik ana dala girerken otomatik olarak derlenir ve test edilir. Amaç, entegrasyon hatalarını saatler sonra değil dakikalar içinde bulmak.
  • CD (sürekli teslim/dağıtım): testleri geçen sürüm otomatik olarak paketlenir ve istenen ortama (staging, canary, production) çıkar. Teslim (delivery) son onayı insana bırakabilir; dağıtım (deployment) otomatiktir.

ML'de CI, normal yazılım testlerine ek olarak veri sözleşmesi, model eğitimi yakınsaması, kalite eşiği ve pipeline entegrasyonu içerir. Google'ın MLOps modelinde Level 2 tam olarak budur: pipeline kodunun kendisi test edilir ve dağıtılır.

GitHub Actions sözlüğü

GitHub Actions depoda .github/workflows/*.yml dosyalarını okur.

  • iş akışı (workflow) — Anlam: Bir YAML dosyası; bir veya daha çok job içerir
  • event — Anlam: Workflow'u tetikleyen olay: push, pull_request, schedule, workflow_dispatch
  • job — Anlam: Aynı runner üzerinde çalışan adım grubu; varsayılan olarak paralel
  • step — Anlam: Tek komut (run:) veya hazır action (uses:)
  • koşucu (runner) — Anlam: İşi çalıştıran makine: GitHub-hosted ubuntu-latest ya da self-hosted
  • matrix — Anlam: Aynı job'u parametre kombinasyonlarıyla çoğaltma (ör. Python 3.11/3.12)
  • iş artefaktı (artifact) — Anlam: Job'lar arasında taşınan dosya (model, metrik, rapor)
  • gizli değer (secret) — Anlam: Şifreli ortam değişkeni; loglarda maskelenir
  • bağımlılık önbelleği — Anlam: Paket kurulumlarını job'lar arasında saklayıp süreyi kısaltma

Tipik bir ML akışı:

  1. pull_request → lint + unit testler + veri şeması testleri (hedef: < 5 dk).
  2. push (main) → küçük veriyle uçtan uca eğitim, kalite kapısı, model artifact'ı.
  3. schedule (gece) → tam veriyle eğitim, dilim analizi, drift raporu.
  4. workflow_dispatch → elle onaylı dağıtım; environment ile korumalı ortam.

Neden her PR'da tam eğitim yapmıyoruz? Maliyet ve geri bildirim süresi. 40 dakikalık bir job'u her PR'a koyarsan geliştirici ya bekler ya da testleri atlar. PR'da duman testi (küçük veri, 1-2 epoch), gece tam eğitim.

Anlatım02 / 12

ML CI'ı tasarlamak: neyi, nerede, hangi eşikle?

Üç katman

Katman 1 — PR kapısı (dakikalar). ruff/mypy, pytest -q, veri şeması testleri, tek örnekte çıkarım, python -c "import model". Model eğitilmez veya 30 satırla 10 saniye eğitilir. Amaç: sözdizimi, sözleşme ve bariz mantık hataları.

Katman 2 — merge/gece kapısı (10-60 dk). Küçük ama gerçek veriyle uçtan uca eğitim; eval_gate.py kalite eşiği; önceki sürüme göre regresyon toleransı; dilim metrikleri; artifact olarak model.joblib + metrics.json.

Katman 3 — dağıtım (saatler). Container build, staging'de API/load testi, canary (%1 trafik), metrik gözlemi, geri alma tatbikatı.

Kalite kapısı = kod

Eşikleri YAML'a gömmek yerine ayrı bir betikte tut: yerelde de aynı betiği çalıştırabilirsin, test edilebilir, versiyonlanır. Kapı iki şeyi kontrol eder:

  1. Mutlak eşik: accuracy >= 0.90, roc_auc >= 0.95.
  2. Regresyon toleransı: yeni metrik, önceki sürümün metriğinden tol'dan fazla düşmemeli. Sadece mutlak eşik koyarsan model yavaş yavaş 0.91'e kadar erir ve kimse fark etmez.

Eşiği veriden bağımsız seçme: sınıf dengesizse accuracy yanıltır, PR-AUC veya dilim bazlı recall kullan. İş metriğiyle ilişkiyi (ör. her 0.01 AUC = kaç TL) belgeleyen bir tablo, eşiğin neden 0.95 olduğunu açıklar.

YAML tuzakları

  • on anahtarı. PyYAML gibi YAML 1.1 ayrıştırıcıları onu boolean True sanar. GitHub YAML 1.2 kullanır; yerel doğrulamada "on": yaz veya BaseLoader kullan.
  • ${{ }} ifadeleri. GitHub'ın kendi şablon dili; Python f-string'iyle karıştırma. Bash içinde tırnak: run: echo "${{ github.sha }}".
  • Gizli değerler. Fork'tan gelen pull_request çalışmalarına secret verilmez (güvenlik). pull_request_target ise secret verir ama fork kodunu çalıştırırsan ciddi güvenlik açığıdır; kullanma.
  • İzinler. Varsayılan GITHUB_TOKEN geniştir. permissions: contents: read ile daralt; yalnız gereken job'a packages: write ver.
  • Eşzamanlılık. Aynı dala art arda push'ta eski çalışmayı iptal et: concurrency: {group: ci-${{ github.ref }}, cancel-in-progress: true}.
  • Action sürümü. @v7 gibi major etiketleri hareket eder. Yüksek güvenlikli ortamda tam SHA'ya sabitle (actions/checkout@<40 karakter sha>), Dependabot ile güncelle.
  • Önbellek. cache: pip anahtarı requirements.txt içeriğine bağlıdır; dosya değişince yenilenir. Veri önbelleğini anahtarlarken veri sürümünü de yaz, yoksa bayat veriyle eğitirsin.

Ölçülebilir hedefler

  • PR pipeline p95 süresi < 10 dk, başarısızlık oranı < %5 (kararsız test yok).
  • Gece pipeline'ı her gün yeşil; kırmızıysa 24 saat içinde ya düzeltilir ya test karantinaya alınır ve issue açılır.
  • Dağıtım geri alma süresi < 10 dk; tatbikatı çeyrekte bir.
Kod03 / 12

Kalite kapısı betiği: iyi model geçer, bozulmuş model eşik ve regresyon kontrolünde durur. sys.exit(1) CI adımını kırmızıya çevirir.

# test: python 3.13 · scikit-learn 1.9.1
# eval_gate.py — model kalite kapısı: CI'da "merge edilebilir mi?" kararı
# PC'de çalıştır: python eval_gate.py
import json, math, sys
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import accuracy_score, roc_auc_score

THRESHOLDS = {"accuracy": 0.90, "roc_auc": 0.95}

def train_and_measure(C=1.0, seed=0):
    X, y = load_breast_cancer(return_X_y=True)
    Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.25, stratify=y, random_state=seed)
    clf = make_pipeline(StandardScaler(), LogisticRegression(C=C, max_iter=5000)).fit(Xtr, ytr)
    p = clf.predict_proba(Xte)[:, 1]
    return {"accuracy": float(accuracy_score(yte, p >= 0.5)),
            "roc_auc": float(roc_auc_score(yte, p))}

def gate(metrics, baseline=None, tol=0.01):
    problems = []
    for name, floor in THRESHOLDS.items():
        v = metrics[name]
        if not math.isfinite(v):
            problems.append(f"{name} sonlu değil ({v})")
        elif v < floor:
            problems.append(f"{name}={v:.4f} < eşik {floor}")
        if baseline and v < baseline[name] - tol:
            problems.append(f"{name} geriledi: {v:.4f} (önceki {baseline[name]:.4f})")
    return problems

current = train_and_measure(C=1.0)
print("current:", {k: round(v, 4) for k, v in current.items()})
print("gate    :", gate(current) or "GEÇTİ")

with open("metrics.json", "w") as f:
    json.dump(current, f)

bad = train_and_measure(C=0.0001)
print("\nbozuk model:", {k: round(v, 4) for k, v in bad.items()})
problems = gate(bad, baseline=current)
print("gate    :", problems or "GEÇTİ")

if problems:
    print("CI adımı çıkış kodu 1 ile durur.")
    sys.exit(1)

# Çıktı (sondaki exit=1 kasıtlı: ikinci model kapıyı geçmiyor):
# current: {'accuracy': 0.958, 'roc_auc': 0.9952}
# gate    : GEÇTİ
#
# bozuk model: {'accuracy': 0.6434, 'roc_auc': 0.9618}
# gate    : ['accuracy=0.6434 < eşik 0.9', 'accuracy geriledi: 0.6434 (önceki 0.9580)', 'roc_auc geriledi: 0.9618 (önceki 0.9952)']
# CI adımı çıkış kodu 1 ile durur.
# exit=1

Gerçek CI'da bu betik pytest'ten sonra çalışır; çıkış kodu 0 değilse job başarısız olur ve PR merge edilemez.

Kod04 / 12

Workflow dosyası ve yerel doğrulama. GitHub Actions'ı yerelde çalıştırmak için act var; ama önce YAML'ın doğru olduğunu ve job grafiğinin beklediğin gibi olduğunu gör.

# check_workflow.py — workflow dosyasını yerelde doğrula (push etmeden)
# PC'de çalıştır: pip install pyyaml
import yaml

print("tuzak:", yaml.safe_load("on: push"))          # YAML 1.1 'on'u True sanır

WORKFLOW = """
name: ml-ci
"on":
  pull_request:
  push:
    branches: [main]
  schedule:
    - cron: "0 3 * * *"
  workflow_dispatch:

concurrency:
  group: ml-ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    strategy:
      matrix:
        python-version: ["3.11", "3.12"]
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: ${{ matrix.python-version }}
          cache: pip
      - run: pip install -r requirements.txt
      - run: pytest -q --maxfail=1

  train:
    needs: test
    if: github.event_name != 'pull_request'
    runs-on: ubuntu-latest
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
          cache: pip
      - run: pip install -r requirements.txt
      - run: python train.py --out model.joblib
      - run: python eval_gate.py
      - uses: actions/upload-artifact@v7
        with:
          name: model
          path: |
            model.joblib
            metrics.json
          retention-days: 7
"""

wf = yaml.safe_load(WORKFLOW)
print("workflow :", wf["name"])
print("tetikler :", list(wf["on"]))
for job, spec in wf["jobs"].items():
    matrix = spec.get("strategy", {}).get("matrix", {}).get("python-version", [])
    deps = spec.get("needs", "-")
    cond = spec.get("if", "-")
    print(f"job {job:6s} needs={deps:5s} matrix={matrix or '-'} if={cond}")

problems = []
for job, spec in wf["jobs"].items():
    uses = [s.get("uses", "") for s in spec["steps"]]
    if not any(u.startswith("actions/checkout@") for u in uses):
        problems.append(f"{job}: checkout yok")
    if not any(u.startswith("actions/setup-python@") for u in uses):
        problems.append(f"{job}: setup-python yok")
if wf["jobs"]["train"].get("needs") != "test":
    problems.append("train, test'e bağlı değil")
print("sorunlar :", problems or "yok")

# Çıktı:
# tuzak: {True: 'push'}
# workflow : ml-ci
# tetikler : ['pull_request', 'push', 'schedule', 'workflow_dispatch']
# job test   needs=-     matrix=['3.11', '3.12'] if=-
# job train  needs=test  matrix=- if=github.event_name != 'pull_request'
# sorunlar : yok

Dosyayı .github/workflows/ml-ci.yml olarak kaydet. actions/checkout@v7 ve actions/setup-python@v7 sürümleri 2026-11 itibarıyla güncel major sürümler; üretimde SHA'ya sabitle.

Anlatım05 / 12

Pratik: Titanic deposuna CI/CD ekle

Görev. Bir önceki derste yazdığın test_titanic.py ve modelini kullanan küçük bir depo kur; GitHub Actions ile üç katmanlı akışı çalıştır.

  1. Depo yapısı. src/features.py, src/train.py, tests/test_titanic.py, requirements.txt (sürümleri sabitle: scikit-learn==1.9.1 gibi), .github/workflows/ml-ci.yml.
  2. PR job'u. ubuntu-latest, Python matrisi ["3.11", "3.12"], cache: pip, pytest -q --maxfail=1. Testler CSV'den okusun; ağ yok.
  3. Eğitim job'u. needs: test, if: github.event_name != 'pull_request'. Küçük veriyle python src/train.py --sample 300 --out model.joblib, sonra python eval_gate.py. metrics.json ve model.joblib artifact olarak yüklensin (retention-days: 7).
  4. Gece job'u. schedule: cron "0 3 * * *" (UTC; Türkiye 06:00). Tam veri, 5-katlı CV, dilim raporu; continue-on-error: false.
  5. Korumalar. permissions: contents: read, concurrency ile iptal, timeout-minutes, workflow_dispatch ile elle tetikleme.
  6. Kanıt. Bir PR aç: test kırmızıyken merge butonu kapalı olmalı (branch protection → required status checks). Testi düzelt, yeşil olduğunu gör. Sonra eval_gate.py eşiğini geçici olarak 0.99 yap; eğitim job'u kırmızıya dönsün.

Beklenen sonuç. PR'da ~2-3 dk, eğitim job'u ~1 dk (300 satır). Actions sekmesinde job grafiği: test (3.11), test (3.12) paralel; ikisi de yeşilse train başlar. Kırmızı job'un logunda hangi adımın ve hangi testin düştüğü görünür.

İpucu. act pull_request -j test ile workflow'u Docker'da yerel çalıştırabilirsin (secret'lar ve GitHub-hosted image farkları olabilir). gh run watch ile canlı izle; gh run download ile artifact'ı indir. actions/setup-python cache'i ilk çalıştırmada ısınır, ikinci çalıştırmada pip install süresi belirgin düşer.

Ek pratik. Aynı workflow'u reusable workflow'a çevir (workflow_call) ve iki depodan çağır. Sonra pull_request ile gelen bir katkıda secret'ların neden görünmediğini loglarda doğrula.

Kontrol06 / 12

Yerelde yaml.safe_load('on: push') çıktısı {True: 'push'} oluyor. GitHub'da workflow neden yine de doğru çalışıyor?

Cevabı göster

GitHub Actions YAML 1.2 ayrıştırıcısı kullanır; orada on düz bir anahtardır. PyYAML varsayılan olarak YAML 1.1 uyumludur ve on/off/yes/no gibi sözcükleri boolean sayar. Yerel doğrulamada anahtarı "on": diye tırnakla veya yaml.BaseLoader kullan; aksi halde kendi kontrol betiğin tetikleyicileri göremez.

Kontrol07 / 12

Neden her pull_request çalışmasında tam veriyle model eğitmiyoruz? İki somut maliyet ve bir çözüm söyle.

Cevabı göster
  1. Süre: 40 dakikalık eğitim, PR geri bildirim döngüsünü öldürür; geliştirici ya bekler ya testleri atlar. 2) Maliyet: her PR'da GPU/CPU dakikaları ve veri erişimi harcanır; fork PR'larında secret ve veri erişimi zaten kısıtlıdır. Çözüm: PR'da küçük örnekle duman eğitimi ve unit testler; tam eğitim main'e merge'de veya gece zamanlanmış job'da.
Kontrol08 / 12

eval_gate.py yalnızca mutlak eşik (accuracy >= 0.90) kontrol ediyor. Hangi kör noktayı bırakır, nasıl kapatırsın?

Cevabı göster

Model 0.905'te takılıp her sürümde biraz daha kötüleşirse mutlak eşik yeşil kalır; yavaş erime (slow leak) görülmez. Önceki sürümün metriğini baseline olarak saklayıp tolerans kontrolü ekle (yeni < eski - 0.01 ise kırmızı). Ayrıca tek küresel metrik yerine önemli dilimlerde (cinsiyet, sınıf) eşik koy; dengesiz veride accuracy yerine PR-AUC/recall kullan.

Kontrol09 / 12

Bir PR'da workflow'a pull_request_target ekleyip fork'tan gelen kodu run: ile çalıştırıyorsun. Risk nedir?

Cevabı göster

pull_request_target secret'lara ve yazma token'ına erişir; fork'tan gelen güvenilmeyen kodu çalıştırırsan saldırgan secret'ları okuyabilir veya depoya zarar verebilir. Fork PR'larında pull_request kullan (secret yok, salt okunur token); güvenilmeyen kodu asla ayrıcalıklı bağlamda çalıştırma. Gerekirse iki aşamalı iş akışı: ayrıcalıksız job artifact üretir, ayrıcalıklı job yalnız doğrulanmış artifact'ı işler.

Soru10 / 12

Aynı dala arka arkaya iki push geldi. İki iş akışı paralel koşuyor, ikisi de aynı içerikle model artifact'ını yüklüyor ve kaynakları ikiye katlıyor. En doğrudan düzeltme?

Seçenekler

Aynı group altındaki koşular sıraya girer; cancel-in-progress eskiyi iptal eder. Aksi halde iki koşu aynı anda hem artifact hem ortam üzerinde yarışır ve sonuç, biten koşunun sırasına bağlı kalır.

Soru11 / 12

Workflow schedule: cron "0 21 * * *" ile tanımlı ve runner'lar UTC kullanıyor. Türkiye UTC+3 iken yerel saatle saat kaçta koşar?

21+3=24≡021+3 = 24 \equiv 021+3=24≡0, yani ertesi gün 00:00. cron her zaman UTC'dir; yerel saat varsayımı 'gece işi sabah koştu' sınıfı sürprizleri üretir.

Özet12 / 12
  • CI her değişiklikte test eder; CD testleri geçen sürümü paketleyip ortama çıkarır. ML'de veri ve model kalitesi de kapıdır.
  • GitHub Actions: .github/workflows/*.yml; event → job → step; matrix, cache, artifact, secret, concurrency, permissions.
  • Katmanlar: PR'da saniyeler/dakikalar (lint, unit, şema), merge/gece tam eğitim + kalite kapısı, dağıtımda canary ve geri alma.
  • Kalite kapısını kod olarak yaz: mutlak eşik + önceki sürüme göre regresyon toleransı + dilim metrikleri.
  • Tuzaklar: YAML 1.1 on sorunu, fork secret'ları, pull_request_target riski, geniş token izinleri, sabitlenmemiş action sürümleri, bayat cache.
  • Ölç: pipeline süresi, kararsızlık oranı, geri alma süresi.
